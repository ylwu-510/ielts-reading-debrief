# 复盘数据与构建器

`build_review.py` 将已经核对的复盘内容写入 Word；它不执行 OCR，不判断答案，不替代阅读分析。运行 `--check-only` 只需要 Python 标准库，生成 Word 另需 `python-docx`。脚本不联网、不安装软件。

```bash
python scripts/build_review.py review.json --check-only
python scripts/build_review.py review.json --output 阅读复盘.docx
```

默认载入 `assets/review-template.docx`，保留页面、页脚和样式，并根据 `assets/word-style.json` 生成五部分内容。`--cjk-font`、`--english-font` 可覆盖字体；覆盖同时作用于样式、正文、表格和页脚。指定字体必须由使用者的系统提供；脚本不检测或安装字体，实际字体替换与分页应通过渲染检查。

## 数据结构

所有文字为普通文本，不在 JSON 中写 Markdown 加粗。短证据关键词放在 `emphasis` 数组；长引文、解释正文保持常规字重。`id` 可用题号整数或字符串；错因代码必须保留前导零。

## 核对状态与分数

- `answers` 应记录本篇所有题目；成绩与题型正确数从该数组计算，不接受手写总分。
- `correct` / `wrong` 要有可靠 `key`，并填写 `answer_source` 指向 `sources[].id`，说明答案判定依据来自哪份材料；不能把来源仅留在聊天上下文中。未知答案用 `unverified`，`key` 可为 `null`，`answer_source` 可省略；填写了则也必须指向已声明的来源。未作答的 `user_answer` 用空字符串。
- `status` 已表达核对状态，不另设重复的核验字段。Word 在文末集中列出答案来源与题号；待核对题保留状态，不因附有来源就被当作已经判定。来源字段检查只能证明关联存在，不能代替人工核对来源可靠性。
- `key` 可以是字符串或可接受答案数组，例如 `["colour", "color"]`。多个词组成的一个答案仍用一个字符串。
- 脚本按忽略大小写、合并空白的方式做字面一致性检查。字面不同但经核对应判对（或相反）时，先复核；确有理由再填写可选 `marking_note`。不能用它掩盖尚未核对的答案。
- `unverified` 单列为待核对，不混入错题和错因统计；存在待核对时不显示容易误解的完整篇章分数。
- 所有已确认答错的题目必须在 `questions` 中出现。可补充有价值的正确题或待核对题；这两类的 `cause` 使用 `null`，避免强行归因。

## 每一道题的定位路线

顶层 `answer_routes` 为必填数组，与 `answers` 的题号一一对应，覆盖正确、错误和未核对题。不能漏掉正确题，不能重复或增加不存在的题号；数组本身可按任意顺序录入，Word 始终按 `answers` 顺序展示。

| 路线状态 | 必填内容 | 适用边界 |
| --- | --- | --- |
| `verified` | `source`、`entry`、`path`、`location`、`check`、`time_saver` 均为非空文本 | 对应答案已经核对；`source` 指向已声明的原文来源 |
| `pending` | 非空 `reason` | 材料不完整或路线尚未核对，保留真实已知内容，不编造位置 |

`pending` 可填写已经有依据的入口、路径、位置、核对条件和 `time_saver`；填写的文本不得为空，`source` 必须关联有效来源。两种状态均可加短文本 `if_stuck`，表示卡住时先放下什么、稍后怎样回查。路线的 `pending` 不会改变答案的正确状态，也不会增减错题或成绩。

一条有效路线必须从考场做题前就能识别的信息出发：

- `entry`：题干中的名称、特殊词、限制条件、空格词性或信息关系；不能用已经知道的答案反过来充当入口。
- `path`：如何用这个入口扫读、识别改写、缩小范围并找到候选。只写“A 段”或“搜索正确答案词”不构成路径。
- `location`：最终核对的段、句或相关核查范围，便于回查。
- `check`：找到后还需核对哪些对象、动作、条件和逻辑，避免停在一个相似词上。
- `time_saver`：具体少做哪一步，如“接上题同句后半取词，免去重新全文检索”；或说明最小充分阅读范围与停止扩读条件。不能只重复段号或空泛地说“快速扫读”，也不能声称这是用户已经被证实的耗时行为。

NOT GIVEN 的 `location` 写实际核查范围，`check` 写原文尚未建立的关系或缺失信息；不要假造“答案句”。标题题的路线也要体现如何从段落整体判断中心，不能把某个细节词等同主旨。

Word 在“02 逐题复盘”最前放置“每题定位与提速”三列表格：题号、从哪里找、确认与省时动作。第二列按“入口 → 搜索路径 → 位置”分短行展示；第三列先写核对条件，再以青绿色“省时”短标签显示 `time_saver`，最后放可选的暂放动作。随后保留原有错题六字段；正确题只需这条短路线，除非另有值得展开的疑点。

旧数据需补齐此数组；不充分的题目先如实写 `pending`，不要为了通过校验补猜内容。脚本验证覆盖、状态、字段和来源关联，不自动判断路线是否真能从题干出发，分析者仍需核对路线质量。

## 用户强调速度时的整篇方案

用户提出超时、做得慢或要求提速时，填写可选对象 `method.speed_plan`。不强调速度的旧数据仍可省略；一旦提供，以下字段均必填且为非空文本，`steps` 必须是非空数组：

```json
{
  "context": "本次提速目标与已知计时背景；区分本篇、其他练习以及限时后成绩。",
  "steps": [
    {"stage": "先处理具体入口题组", "action": "说明从题面什么线索开始、怎样处理与复用题目。", "saves": "明确省去的重复操作，而非虚构节省分钟数。"}
  ],
  "stop_rule": "何时暂放、留下什么最小标记、何时只回查缺项。",
  "practice": "新材料预算与截止记录；同时比较正确数、完成情况和用时。"
}
```

该对象显示在模块04开头的“本篇提速路线”，三列表格后给暂放与练习规则，再保留原有五项方法提示。一般两至四步即可；不要求每一步重新通读，不以已知答案作为第一步依据。它是建议方案，不是历史耗时记录，不能填入 `overview.timing` 冒充本篇实测数据。

## 计时与速度短板

`overview.time` 仍接受原来的自由文本。若有明确计时，推荐额外填写 `overview.timing`；它会优先于 `time` 显示：

```json
{
  "scope": "passage",
  "elapsed_minutes": 23.5,
  "budget_minutes": 20,
  "basis": "用户的手机秒表记录；从开始读题到最后填答。",
  "completion_note": "已完成全部题目，末尾没有回查。"
}
```

- `scope` 必填：`full_test` 为整套阅读、`passage` 为单篇、`question_group` 为题组，不能把单篇用时当整套成绩依据。
- `elapsed_minutes` 必填；`budget_minutes` 可选。两者必须为正有限数，单位为分钟，不接受布尔值、零、负数、NaN 或无限值。
- `basis` 必填，说明记录来源与计时边界。`completion_note` 可选，用于说明是否完成、是否包含回查等。

有预算时显示实际用时、预算和差值：如“实际 23.5 分钟；预算 20 分钟；超时 3.5 分钟”。用时低于预算显示余量，等于预算显示一致。没有预算就只报告范围和实际用时，不自动设定目标，也不据此断言超时。差值只描述给定计时与预算的关系；尚未完成的练习不能仅凭余量认定速度达标。

速度短板应结合记录、每题路线和完成情况解释；不能从错题或高亮数量推算耗时。脚本不提供考官分数，也不将单篇结果换算为整套阅读 Band。

## 逐题六字段

`作答结果` 从 `answers` 自动取得；另外五字段由 `requirement`、`evidence`（NOT GIVEN 可用 `evidence_review`）、`comparison`、`cause`、`action` 生成。题目要求和正确证据各允许一段简短说明。暂时不能确定个人错因时也保留六字段，不强行归类。

固定错因代码：`01 词句没读懂`、`02 换个说法没认出`、`03 证据没找到`、`04 题目要求没查全`、`05 相似内容选混了`、`06 答案填写出错`。

`cause.observation` 写已经知道的答案缺口、标记或作答观察，不能把“可能漏看条件”写成已经证实的个人原因。Word 在同一“错因判断”字段先写这一观察，再列个人原因状态。按可用证据选择状态：

| `certainty` | `code` | 还需填写 | Word 呈现 |
| --- | --- | --- | --- |
| `confirmed` | 一个 `01`—`06` 代码 | `basis`：用户复述的当时过程或当时留存记录；不能用看过解析后的自测表现倒推历史原因。`candidates` 留空或省略 | 已确认原因及确认依据 |
| `possible` | 优先排查的一个代码 | `self_check`；可用 `candidates` 补充其他待排查类别 | 优先排查主因，以及候选 |
| `unconfirmed` | 显式 `null` | `self_check`；可选 `candidates`，没有足够依据时可为空 | 待确认，尚未归类；有候选时另列候选 |

`candidates` 是不重复的代码数组，不得再次包含主因 `code`。它表示需要通过反馈区分的解释，不表示同一道题已经确认存在多个错误。例如：

```json
{"code": null, "certainty": "unconfirmed", "observation": "答案对应了部分信息，但没有当时的思路记录。", "candidates": ["04", "05"], "self_check": "当时是否已经核对题干所有限制，再比较两个候选？"}
```

### 错因汇总与后续反馈

`causes` 保持三列表格；每行包含 `status`（`confirmed` 或 `pending`）、`code`、`question_ids` 和 `training`。按逐题当前状态精确汇总：

- `confirmed` 主因进入对应的 `confirmed` 行。
- `possible` 主因和所有候选，各进入对应的 `pending` 行。
- `unconfirmed` 有候选时，各进入对应的 `pending` 行；没有候选时进入 `status: "pending", code: null` 的未归类行。

同一代码可有一条已确认行和一条待排查行，不得重复相同的 `(status, code)`。`code: null` 只用于待确认且没有候选的题目。旧数据省略 `status` 时，脚本依据题目状态推定；同一代码混合两种状态的行必须拆开，不能默认为已确认。

一个题号可以出现在不同候选行，但仍只算一道错题。出现此情况时，Word 会明确提示候选数不能相加作为错题数。得到关于当时作答过程的反馈后，同时更新逐题 `cause` 与 `causes`，删去被排除的候选；有足够依据确认原因时补上 `basis`，清空候选。后续自测可用于选择训练方向，不能单独证明最初的个人错因。校验会拒绝遗漏或残留的汇总，不修改用户数据来自动消除矛盾。

## 原文引用

每个证据或高亮条目通过 `source` 指向 `sources[].id`。`sources[].text` 可省略，例如只有扫描图时；此时脚本不能验证摘录真伪，须由分析者对照图像检查。

当 `text` 可用时，脚本要求 `quote` 是合并空白后可找到的连续摘录，避免生成过程中改写原文。需要不连续的两句时，将它们放进两个 `evidence` 对象，不插入省略号后冒充连续原句。`emphasis` 必须逐字存在于引文中，单项最多 12 个英文词或 80 字符；长引文不得加粗大半篇幅。

这是文本一致性检查，不能证明证据足以支持答案，也不能自动核对页面高亮。

### 不同题型的证据

`questions[].evidence_type` 默认是 `direct`，用于通常的直接对应。另有三种：

- `contradiction`：FALSE / NO 等明确矛盾。仍须引用真实原文，并在解释中指出同一对象、条件及相反关系；不是“没有找到就是 FALSE”。
- `main_idea`：标题、主旨等整体判断。仍须引用真实原文，解释如何覆盖段落或全文的核心内容，以及原选项为什么只覆盖局部、范围偏大或重点不同。脚本无法代替这项内容判断。
- `not_given`：信息不足。允许 `evidence: []`，但必须补 `evidence_review`；不能编造一句“不存在的信息”作为原文。若逐题复盘中的 `key` 为 `NOT GIVEN` / `NG`（不区分大小写），必须使用此模式。反过来，`key` 明确为 `TRUE` / `FALSE` / `YES` / `NO` 时不能使用此模式绕过原文证据。

NOT GIVEN 示例字段：

```json
{
  "evidence_type": "not_given",
  "evidence": [],
  "evidence_review": {
    "source": "passage",
    "scope": "A 段全部内容及前后涉及开放安排的语境。",
    "missing_information": "文章给出了开放时间，但未说明访客是否需要支付入场费。"
  }
}
```

`source` 必须指向已声明来源，`scope` 明确已核查的范围，`missing_information` 明确题干需要但原文没有建立的信息或关系。Word 仍使用“正确证据”字段，显示核查范围及缺失信息。可在 `evidence` 中补充相关上下文的真实引文，但即使有上下文，仍需这两个说明。三个字段是否存在可以自动校验；核查范围是否充分、是否确实未说明，须由分析者核对。

`main_idea` 与 `contradiction` 始终要求引文。其他未核对题使用默认 `direct` 时，可暂时留空引文，并在文档中明确标记缺少可核对证据。

## 高亮数据

有实际标记图像，或用户明确提供了可核验的高亮文字记录，并已对照核查时，使用 `status: "observed"`。文字记录须能确定位置及用户实际标了什么；没有图像时，描述为“依据用户高亮文字记录”，不能假称看过截图。三组均为数组，没有建议时可为空：

```json
{
  "status": "observed",
  "add": [
    {"source": "passage", "location": "A 段 / 第 1 题", "observed": "已标了方法词，未见时间条件的标记。", "quote": "应补标的原文短语", "reason": "说明它怎样帮助核对要求。"}
  ],
  "reduce": [
    {"source": "passage", "location": "B 段", "observed": "实际已经标过的连续原文", "action": "缩为具体哪几个词，或取消", "reason": "说明定位或证据用途，而非仅以长短判断。"}
  ],
  "keep": [
    {"source": "passage", "location": "C 段 / 第 2 题", "observed": "实际已经标过的连续原文", "reason": "说明有效用途。"}
  ],
  "question_adjustments": "题干中需要同步保留的限制条件。",
  "boundary": "未标不等于没读懂；不要以事后已知答案要求预知所有答案位置。"
}
```

`add.observed` 为对真实标记的描述；`add.quote` 为建议补标的原文。`reduce.observed`、`keep.observed` 应是用户实际标出的原文，源文本可用时也会逐字检查。既没有实际标记图像，也没有用户明确提供的可核验高亮文字记录时，必须使用 `not_provided`，并留空三组；不能把原文本身或自己的高亮建议当作用户标记记录。

三组每行都可增加 `priority: "core"`（默认）或 `"optional"`。同组先展示核心条目，再展示可选条目；同优先级保持输入顺序，可选行的位置标注“可选”。用可选项容纳有余力时再调整的标记，不把所有修改都当成必须执行的任务；字体、字号和颜色保持原有样式。

## 分页与输出检查

默认正文随内容自然分页，高亮修改从新页开始。标题与后续段落绑定、表头重复、表格行不跨页。需要分组时，可在某题设置 `break_before: true`，或用 `layout.break_before_sections` 指定 `02`—`05`，覆盖默认的 `["05"]`；显式空数组表示全部自然分页。不默认每题一页。

保留五个模块；逐题复盘用段落，概况、错因汇总及高亮修改用紧凑表格。高亮通常控制在一页，内容过多时优先筛选影响解题的修改，不缩小正文来硬塞。生成后逐页渲染检查：正文与关键短语层级、中文粗体、表格跨页、页尾孤行、页面密度及字体替换。`--check-only` 成功不代表完成视觉检查。
